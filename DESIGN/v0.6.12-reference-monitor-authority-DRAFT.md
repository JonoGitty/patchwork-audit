## CORRECTED DIRECTION (post red-team — this is the accepted shape)

The draft's fatal premise: it treated the same-UID PreToolUse hook as the enforcement gate. It isn't. Per GPT-5.5:

1. **The same-UID hook is "an adversary-controlled courier," not an authority.** No same-UID primitive (peer-cred, PID, path, even code-signature) distinguishes the legitimate hook from the agent running that same hook binary with adversarial input. Treat every ToolEvent from the hook as attacker input. The hook is telemetry + preflight UX, NOT the reference monitor.

2. **O1 containment is PRIMARY; the daemon is the control plane, not the gate.** Slogan: *daemon as control plane, OS sandbox as enforcement plane. A daemon without containment is not a Mythos reference monitor.* The agent routes around any hook via child processes, `python -c`/`node -e`, `/dev/tcp`, DNS, static binaries, package scripts. Only OS-level containment (sandbox-exec/Seatbelt on macOS, seccomp/landlock/namespaces on Linux) actually stops that.

3. **The architecture must SUPERVISE execution, not observe it.** Shift from "agent spawns hook → hook calls daemon" to "**a root supervisor LAUNCHES the agent + all descendants inside an OS sandbox**, handing trusted capabilities (Mach port/XPC w/ code-signing requirement, or inherited FD) only to components the agent can't impersonate." You cannot retroactively protect an arbitrary already-running agent.

4. **Approval**: a plain menubar click is NOT acceptable (Accessibility/CGEvent can synthesize it). The achievable bar is a **Secure-Enclave/TouchID-signed approval manifest** (notarized approval app holds a Keychain key gated by `biometryCurrentSet`, signs daemon nonce + canonical manifest). Irreducible residual: human-confusion + compromised local display. Push-to-phone / hardware token is higher assurance.

5. **The binding manifest is approval-UX + audit, NOT complete enforcement.** TOCTOU everywhere (files/symlinks/dynamic imports/lifecycle scripts change after hashing). The only strong binding is executing inside the constrained sandbox. Don't position the manifest as the enforcement mechanism.

6. **Don't parse hostile input as root.** Split: tiny root supervisor · unprivileged policy worker · separate approval broker · strict IPC schema. State owned by a `_patchwork` user, not ambient root.

7. **MVP for v0.6.12 = "Protected Mode"**, not "root daemon receives hook RPCs" (that's just tamper-evident logging). Protected Mode: `patchwork protect run <agent>` launches the agent + descendants inside OS containment (default-deny network + explicit allowlist, workspace-scoped fs, deny secret locations: SSH/cloud-creds/browser/password stores), daemon owns policy/audit/approval, hooks are telemetry. One platform first (macOS).

8. **Adoption staging**: two explicit modes. **Advisory Mode** = existing hook behaviour, loud "NOT protected / bypassable by same-UID agents" warnings, no enforcement claim. **Protected Mode** = daemon + containment required, refuses to start without them. Never market advisory as secure.

**The one thing the draft got most wrong** (GPT's words): positioning the same-UID hook + manifest as the enforcement mechanism. Enforcement must be OS containment with the agent launched under the supervisor.

**Implication for the tracker**: O1 and D1/D2 are not separate — they merge into one **Protected Mode** workstream, with O1 (containment) as the primary enforcement and the daemon as the control plane that configures it. O1 was already promoted to P0; it's now the *centre* of v0.6.12, not a sibling of the daemon.

> **Original draft below (premise superseded — kept for the record).**

## The property we're building

> Every agent-influenced path to a real-world side effect is mediated by the same fail-closed, tamper-resistant policy authority, with durable provenance and secure human approval where required.

This doc designs that authority. It subsumes M3 (approval), M4 (binding), M8 (audit ledger), M9 (fail-closed), M10 (concurrency), M12 (daemon hardening), and H1 (snapshot authenticity).

## The crux: the same-UID problem

Patchwork's hooks run as the **same UID** as the agent. The agent can read/write anything that UID can. Therefore:

- Any policy/taint/audit/approval state that is same-UID-writable can be tampered by the agent (this is R1-001/008, F2, F3, and the whole "same-user writable security state" finding).
- Any approval gate the agent process can invoke or influence is self-approvable (R3-001, R6-002/F1).
- A regex/parser boundary inside the agent's own process is bypassable by routing around the parser.

**Conclusion: the authority must live at a privilege the agent's UID cannot reach.** On a single-user Mac that means a **root-owned daemon**. There is no same-UID-only design that contains a same-UID adversary; the best a same-UID design achieves is tamper-EVIDENCE (detect after the fact), not tamper-RESISTANCE (prevent).

## Proposed architecture

### 1. `patchworkd` — a root-owned daemon

- Installed as a root service: launchd `LaunchDaemon` (macOS) / systemd system unit (Linux). Install requires one `sudo` step.
- Runs as root (or a dedicated `_patchwork` system user that owns the state, not the human's UID).
- **Owns, root-only-writable:**
  - the policy (`/Library/Patchwork/policy.yml` or `/etc/patchwork/`)
  - the taint + provenance ledger
  - the append-only audit ledger
  - the HMAC/signing keys
  - approval decisions
- Exposes a Unix-domain socket at a root-owned path. Verifies its OWN binary + policy integrity at startup; refuses to run if either is writable by a non-root UID.

### 2. The hook becomes a thin RPC client

- PreToolUse hook (agent UID) sends the normalized ToolEvent to `patchworkd` over the socket and receives a verdict (`allow` / `deny` / `approval_required`). The hook CANNOT decide; it only relays + enforces the daemon's verdict.
- All taint/provenance writes happen IN the daemon (M10 concurrency solved: daemon serialises). The agent has no writable copy of the state.

### 3. Out-of-band approval (the hardest part)

On `approval_required`, the daemon prompts the **human** through a channel the agent cannot drive:

- **Option A (preferred, macOS):** a small root/user LaunchAgent GUI app (menubar) that the daemon signals; shows canonical command + diff + taint source; requires a click + optionally TouchID. The agent process has no handle to this UI.
- **Option B:** the daemon controls a dedicated TTY/console the agent can't write to.
- **Option C:** push-to-phone (out of band entirely).

The agent NEVER receives an approval affordance and cannot synthesize one. `patchwork approve` from the agent's shell is rejected by the daemon (peer is the agent path, not the approval UI).

### 4. Approval→execution binding (M4)

When the daemon approves an action, it records a **manifest**: argv + cwd + resolved-executable-realpath+hash + relevant input-file hashes + package scripts + git config + env allowlist + interpreter search paths. The hook must present a matching manifest at exec time; the daemon revalidates immediately before allowing. Any drift (env, PATH, script contents, symlink, cwd) → re-deny.

### 5. Fail-closed (M9)

If the hook can't reach the daemon, the policy is stale, the daemon's binary/policy fails integrity check, or versions are skewed → the hook denies all high-risk actions. No silent degradation to "advisory."

### 6. What this does NOT solve (needs O1 containment)

The daemon mediates Patchwork-visible tool calls. It does NOT by itself stop:
- a child process spawned by an allowed command doing egress
- `python -c`, `node -e`, `/dev/tcp`, DNS, static binaries
- reads of secrets that then leave via an allowed channel

Those need **actual OS containment (O1)**: network egress allowlist, fs allowlist, process-exec allowlist — enforced at the OS layer (Seatbelt/sandbox-exec on macOS, seccomp/landlock/namespaces on Linux), which the daemon configures. The daemon is the decision authority; O1 is the enforcement substrate. Both are required.

## Open questions for the cross-vendor reviewer (the hard parts)

1. **Same-UID approval authenticity.** SO_PEERCRED / LOCAL_PEERCRED tells the daemon the connecting process's UID/PID — but the agent IS that UID. How does the daemon distinguish "the legitimate PreToolUse hook" from "the agent's own socket client impersonating the hook"? Is there ANY robust same-UID process-identity primitive, or must we accept that the hook channel is spoofable and rely entirely on the out-of-band approval UI for the security-critical decisions?
2. **Un-spoofable approval on a single-user Mac.** What approval channel genuinely can't be driven/forged by a same-UID agent? Can a menubar app's click be synthesized via Accessibility APIs / CGEvent? Does TouchID actually help? Is push-to-phone the only truly out-of-band option?
3. **Is root-daemon + secure-approval the pragmatic ceiling, or is OS-sandbox (O1) actually the primary control** and the daemon secondary? Which should we build first?
4. **Performance.** Every tool call → RPC round-trip to a root daemon. Acceptable latency budget? Caching that doesn't reintroduce a tamperable same-UID cache?
5. **Install/bootstrap.** Requires `sudo`. How does that square with `npm install -g patchwork-audit`? Two-step (`npm i -g` then `sudo patchwork install-daemon`)? What's the upgrade/downgrade-attack story for the daemon binary itself?
6. **Cross-platform.** launchd vs systemd vs Windows service — how much is shared vs platform-specific? Is macOS-first acceptable for v0.6.12?
7. **Graceful degradation vs adoption friction.** Fail-closed-without-daemon is correct for Mythos-tier, but will break every existing v0.6.10/0.6.11 user who hasn't installed the daemon. How do we stage this (opt-in `--mythos-mode` that requires the daemon; default stays advisory)?
8. **What's the MINIMUM viable daemon** for a first shippable v0.6.12 that's a real improvement, vs the full vision? Where's the cut line?

## My current lean (for the reviewer to challenge)

- The root daemon is unavoidable for tamper-RESISTANCE. Same-UID can only give tamper-evidence.
- The approval channel is the part I'm least sure is solvable on a single-user Mac without push-to-phone or a hardware token. I suspect the honest answer is "TouchID-gated menubar prompt is good-but-not-perfect; document the residual."
- O1 (OS sandbox) might actually be MORE important than the daemon for the egress/secret-read paths, and should possibly come first. Want the reviewer's call on sequencing daemon-first vs sandbox-first.
